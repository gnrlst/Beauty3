# Резервные копии HairFlow

Ежедневная облачная задача Sites создаёт копию в 03:00 Europe/Moscow. Хранение: 30 дней. Рабочая D1 и копии в R2 — разные ресурсы; удаление всего проекта Sites может удалить оба. Для защиты от удаления проекта владелец может скачать копию в настройках и хранить её вне Sites. Код и история версий хранятся отдельно в Git.

Копируются все три прикладные таблицы: business_state (весь реестр всех компаний), members (включая отключённых), audit. Копия содержит исходный SQL таблиц и индексов, все столбцы, строки, дату, проект и SHA-256 содержимого. Все SELECT выполняются одним транзакционным D1 batch. Новые прикладные таблицы включаются автоматически; также сохраняется доступная таблица истории миграций. Внутренние таблицы SQLite/Cloudflare исключены. Изменение схемы во время копирования прерывает запуск и требует повтора.

После R2.put копия полностью читается и проверяется, только затем удаляются копии старше 30 дней. Ежедневный ключ привязан к московской дате, повтор задачи проверяет существующую копию. Ручные копии имеют отдельные UUID. Скачивание и ручное копирование доступны только владельцу главной компании, не партнёрам и сотрудникам. Копии содержат конфиденциальные данные всех компаний, включая персональные данные сотрудников.

## Инструкция для облачного запуска

1. Получить актуальные настройки этого опубликованного сайта через Sites get_site. Сохранить siwc_bypass_bearer_token только в памяти. Нельзя записывать токен в файлы, код, команды оболочки, логи или текст расписания.
2. Текущий сайт ограничен только владельцем. POST /api/backups/run полагается на эту платформенную границу: токен передаётся только этому сайту в OAI-Sites-Authorization. Этот путь не экспортирует данные и возвращает только ключ, SHA-256, дату и количество строк. Перед публичным размещением нужно заменить границу на отдельную сервисную авторизацию.
3. Вызвать POST https://hairflow-accounting.bronzeduck2.chatgpt.site/api/backups/run с заголовком OAI-Sites-Authorization: Bearer <актуальный токен>. Выполнять серверный HTTP-запрос, не браузер. Не передавать фиктивную идентичность посетителя. Не менять код, базу или аудиторию; не перепубликовывать сайт для обычного копирования.
4. При необходимости использовать scripts/run-backup.mjs из свежей версии исходников Sites. Скрипт принимает JSON {token,url} через скрытый stdin. Перед использованием исходников подтвердить source access отдельно через обычный source helper. Секретов в репозитории нет.
5. Успех — только HTTP 200 с полями key, sha256 (64 hex), created_at, counts и retention_days=30: ответ выдаётся после проверки копии чтением. При сетевой ошибке допускается повтор с тем же дневным ключом. При ошибке уведомить владельца в этом чате; не считать копию созданной. Сбой отдельной задачи не отменяет будущие запуски. Ожидается ежедневное выполнение, даже если сайт не открыт.
6. Связанное расписание видно в Sites automations. Проверять его enabled и последнюю успешную дату при обслуживании; нельзя утверждать, что все будущие копии гарантированно выполнятся.

## Восстановление

До изменения структуры базы или массового исправления данных создать новую ручную копию. Перед восстановлением сохранить текущее состояние и остановить изменения пользователей. Не восстанавливать данные автоматически по расписанию и не заменять живую базу без согласования конкретной копии с владельцем.

Скачать выбранную копию через настройки владельца. В пустой локальный SQLite:

```
node scripts/restore-backup.cjs /absolute/path/backup.json /absolute/path/new.sqlite
```

Скрипт запрещает перезаписывать существующий файл, проверяет формат/проект/контрольную сумму, создаёт таблицы и индексы, выполняет PRAGMA integrity_check и сравнивает все восстановленные строки с копией. Использовать только доверенные копии, скачанные из этого приложения.

Восстановление живой D1 — отдельная управляемая процедура: применить подходящую версию миграций, перенести проверенные строки в транзакции, подтвердить права, остатки, расчёты и журнал перед включением записи. Копия не содержит секретов среды, инфраструктуры Sites и файлов приложения; OWNER_EMAIL и аудитория сохраняются отдельно настройками платформы. На текущем этапе прикладных файлов пользователей в R2 нет, R2 используется только для копий.

Проверка реализации: tests/backups.test.cjs проверяет полное восстановление на наполненных данных, контрольную сумму, права владельца, идемпотентный дневной запуск, отдельные ручные копии, хранение и отсутствие удаления старых копий при сбое проверки. После публикации отдельно проверены запись и чтение первой реальной копии R2. Проверка восстановления реальной копии в локальный SQLite зависит от скачивания её владельцем; не подменять её тестом на образце.
